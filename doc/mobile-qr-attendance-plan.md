# Mobile app QR attendance

## Goal and success criteria

Support the student's KLAS mobile WebView flow: open KW attendance, choose the exact course, complete additional verification, and submit the instructor's decoded QR string with the authenticated session. The SDK must work in CLI, mobile, and other Dart programs without opening UI or obtaining QR input itself. Ordinary clients must automatically apply mobile app identity throughout attendance requests and never infer success from an unknown response.

## Scope

Extend attendance subject lookup and course binding with mobile subject identification, course closing checks, email/registered OTP verification, preparation before external QR input, and strict typed accepted/rejected results. Set the app marker internally per attendance request. Preserve ordinary authentication/feature request defaults and previous captcha work. The caller obtains QR strings and verification answers through its own input mechanism; the SDK sends the original decoded string. Do not implement camera UI, image decoding, CLI prompts, invented QR contents, device/OTP registration, native biometric authentication, or live attendance submission. Already completed server-side app verification can provide the one-time key without a code callback.

## Public API and implementation surfaces

Use ordinary `KlasClient()` configuration for QR attendance. Keep the mobile app identity internal and apply it automatically to attendance subject/list requests and QR closing, certification, email, key and submission requests. Pass immutable headers per request through the catalog and dedicated QR API to the request executor; never mutate shared transport or session identity. Remove the unreleased `KlasClientConfig.mobileApp`, `mobileAppUserAgent` and `userAgent` options. Keep existing `qrCheckIn`/`qrCheckInRaw` signatures compatible with optional `onVerification` and `maxVerificationAttempts`. Replace the unreleased `qrCheckInWithScanner` and `KlasQrScanner` with `course.prepareQrCheckIn` and `attendance.prepareQrCheckIn(subject: ...)`, returning the exported `KlasQrCheckInSession` interface. Its `submit(String qrCode)` returns `KlasQrAttendanceResult`; `cancel()` releases pending preparation locally; `isPending` indicates whether submission remains available. Hide preparation keys and payloads. Claim preparation synchronously when submitting so concurrent calls, rejection, parse failure, and uncertain network failures cannot reuse it. Blank input must not consume a pending preparation. Track an internal session revision to invalidate preparation on login, renewal, or local reset, and reject session changes during verification before any further one-time request. Reuse this preparation implementation for direct typed/raw submission. Export typed challenge/answer/method/callback models and verification-required, verification-failed, and cancelled exceptions. The challenge exposes explicit, coalesced email delivery and registered OTP availability. Verification handlers return null to cancel. One-time operations must still avoid session renewal/replay. Update canonical API/coverage tests, QR-specific regression tests, wiki/API index, coverage, integration guide, README and changelog.

## Validation

Mock HTTP must verify ordinary clients automatically apply the app identity to the entire attendance flow, including read-only retries, without changing login, general features or binary requests. Pause QR verification and issue an unrelated request to check that headers remain isolated. Verify preparation performs no attendance submission, explicit external string input, cancellation, single use including simultaneous calls and uncertain failure, blank-input recovery, and session invalidation. Preserve correct course scope, cookies and certification context; leading zeroes; explicit email delivery; bounded retries; closed courses; missing keys; original QR strings; strict result parsing; and no replay of one-time operations after expiry or uncertain network outcomes. Run scoped analysis, targeted tests, `dart run tool/check_all.dart`, and CLI analysis/build compatibility checks. Preserve previous captcha work. No live state-changing verification is required.

## Constraints

The initial QR implementation was validated in an isolated worktree before integration. Apply this public API correction to the existing feature branch while preserving captcha changes. Inspect only read-only page/code surfaces if more research is needed. Input and UI integration remain the application developer's responsibility. Source research and live account data stay outside the repository; tests use synthetic payloads. Live state-changing account APIs are never used. Final docs must distinguish source/mock verification from actual attendance acceptance.

## Completed validation

The SDK checkout includes automatic attendance headers and program-independent direct/prepared QR submission alongside preserved captcha work. It passed `tool/check_all.dart` with 118 tests, including 34 QR tests and three commit-range regressions. Canonical API/feature coverage and QR lifecycle tests verify external string input, no submission during preparation, local cancellation, single use with concurrent calls and uncertain failures, blank-input recovery, and session changes before submission or during verification. Existing tests still verify header isolation, read-only renewal and no replay of one-time requests. The CLI passed analysis and all 87 tests; its executable compiled against the updated local SDK. Earlier read-only Chrome inspection confirmed course selection and the mobile QR button; no live verification messages, device registrations, or attendance submissions were performed.
